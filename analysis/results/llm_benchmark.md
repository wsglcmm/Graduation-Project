## 觀察

1. **指令理解正確、安全機制有效**：協調 Agent 在模型有回應時的合法率 97.5%（第四步 480 次），各機 Agent 96.6%；不合法的輸出全部被白名單驗證擋下、沒有送出。懸停 / 返航期間 Agent 自行改計畫 0 次。最小 3D 機間距離都 ≥ 5 m（返航多 Agent 有一次 5.4 m：返航不做 C 端去衝突，靠高度層分開 5 m，A 的安全層最後把關）。
2. **LLM 比規則式慢**：每次決策 1.5–3 s（規則式 < 0.1 s），下令包圍要 36–44 s（規則式 25 s）、中途改口抓拍下令後 30–55 s（規則式 17 s）。規則式是針對這個幾何問題手調的，LLM 的價值在聽懂各種說法的自然語言、在做不到時說明原因（例如「降落在屋頂」→ 懸停並說明沒有這個功能），不是比規則式快。
3. **抓拍慢的原因與改善（表 C）**：改善前 LLM 不知道捕捉區在哪，角色照編號固定分（uav1 驅趕、uav3 抓拍），也常派高空監看。`a578198` 把捕捉區與各機相對位置放進世界狀態後，**角色開始依位置分派**（開局的分派和規則式同一型態，例如「封驅拍」），也不再派高空監看。但時間只在單一指揮官明顯縮短（55 → 30 s），多 Agent 沒有改善（31 → 38 s）；每組只有 3 個 seed、標準差 12–17 s，**還不能下結論**。
4. **改善後新看到的兩個問題**：(a) 抓拍期間 LLM 會依最新位置重新分派角色（表 C 的「→」），無人機要重新飛位置，抵銷了好處；規則式在同一次捕捉期間鎖定角色。(b) 單一指揮官 seed 1 沒進入抓拍：目標 predicted（短暫沒看到）時 LLM 回 search，指令被鎖成「只能搜尋」。(b) 已修正（指令意圖不會因為 LLM 先搜尋而被改掉、prompt 說明 predicted 仍可指定目標）。
5. **API 不穩定**：改善後那次執行時 Google 端 503（high demand）57 次，佔請求約 3 成，這些時候沿用上一個計畫或改用規則式。第五步（各機 Agent 也用 LLM）每分鐘約 30 次請求，免費額度不夠，429 約 30%。報告的「合法率」要分成模型輸出與 API 失敗兩部分寫。
6. **剩下的模型不合法輸出**：主要是目標暫時不在清單時沿用上一個計畫的 target_id（11 次），都被驗證擋下。
