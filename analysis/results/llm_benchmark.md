## 觀察

1. **指令理解正確、安全機制有效**：協調 Agent 在模型有回應時的合法率 97.5%（第四步 480 次），各機 Agent 96.6%；不合法的輸出全部被白名單驗證擋下、沒有送出。懸停 / 返航期間 Agent 自行改計畫 0 次。最小 3D 機間距離都 ≥ 5 m（返航多 Agent 有一次 5.4 m：返航不做 C 端去衝突，靠高度層分開 5 m，A 的安全層最後把關）。
2. **LLM 一開始比規則式慢很多**：每次決策 1.5–3 s（規則式 < 0.1 s），下令包圍 36–44 s（規則式 25 s）、中途改口抓拍下令後 31–55 s（規則式 17 s）。
3. **三次改善把抓拍時間從 55 s 降到約 22 s（表 C，同 seed 0–2）**：
   - 找原因：看 events.jsonl，LLM 不知道捕捉區在哪、角色照編號固定分（uav1 驅趕、uav3 抓拍）、常派高空監看。
   - `a578198` 把捕捉區與各機相對位置放進世界狀態 → 角色開始依位置分派、不再派高空監看，但抓拍途中會一直換角色。
   - `22e9476` 同一次捕捉期間鎖定角色（5 次執行中擋下 7 次換角）＋ `ea159d0` 修正指令被鎖成「只能搜尋」的 bug。
   - 結果：單一指揮官 5/5 抓到、下令後 24.7 ± 6.5 s（seed 0–2：54.6 → 22.4 s）；多 Agent 在 LLM 有回應的 3 次都抓到、22.8 ± 5.8 s。和規則式 17.4 s 只差約 5 s，差距主要是 LLM 每次決策的 2–3 s 延遲。
4. **多 Agent 有 2 次沒抓到，原因是 API 額度用完**：那 5 次執行時 Google 回了 190 次 429（免費額度當天用完），下指令後 LLM 一次都沒回應，計畫停在搜尋。這暴露了一個缺口：LLM 長時間失敗時只會沿用最後一個計畫。已修正（`LLM_FAIL_FALLBACK`）：連續失敗 3 次由規則式照操作員有效指令接手，LLM 恢復後交回。Demo 時網路不穩也靠這個。
5. **報告寫法**：這是「實測 → 從紀錄找原因 → 修正 → 再驗證」的完整過程。結論不是 LLM 比規則式好，而是：LLM 負責聽懂自然語言與選策略、確定性程式負責幾何事實與執行穩定性（分層控制），兩者合起來才能接近規則式的效率，又保有自然語言的彈性。
6. **限制**：每組只有 3–5 個 seed；免費額度與 Google 端 503 影響了部分執行（API 失敗已在表中列出）。第五步（各機 Agent 也用 LLM）每分鐘約 30 次請求，免費額度不夠，429 約 30%。
